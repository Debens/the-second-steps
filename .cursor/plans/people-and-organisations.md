# People and organisations — Chunk 2 technical design

**Status:** Technical design approved. Chunk 2A database/security foundation was implemented, verified locally, applied to shared development Supabase, and confirmed up to date on 2026-10-15. Chunk 2B contact application services are implemented and focused-tested locally. Contact UI has not been built.

**Parent plan:** `.cursor/plans/landlord-property-onboarding.md`

## Slice outcome

Add the smallest secure contact foundation needed by later landlord, applicant, tenant, contractor, property, and instruction workflows. Authorised staff can create, view, update, search, and archive a person or organisation within their workspace and branch scope. One record can acquire several business roles later without being duplicated.

This slice includes contact records, contact methods, contact addresses, organisation-person relationships, branch visibility, lifecycle state, readable references, duplicate-candidate queries, permissions, audit events, and focused tests.

It does **not** yet add landlord opportunities, appraisals, properties, ownership, notes, document storage, merging, imports, or external access. Duplicate candidates are shown, but the manager merge operation belongs to Chunk 3.

## Design choice

Use one workspace-owned `Contact` record with a fixed kind of `person` or `organisation`. Person and organisation fields live on that record under a database check constraint; they are not stored in two unrelated roots and are not hidden behind a broad universal-party framework.

This gives later relationships one safe foreign key (`contactId`) while keeping the model understandable:

```text
Workspace
└── Contact (person or organisation)
    ├── ContactPoint (telephone or email)
    ├── ContactAddress
    ├── ContactBranchLink
    └── OrganisationPersonLink (organisation Contact ↔ person Contact)
```

`Contact.kind` is immutable after creation. Correcting a wrongly created kind uses a controlled replacement/merge workflow later; it is not an ordinary edit.

## Proposed tables and fields

Every table below includes `workspaceId`. IDs are UUIDs generated by PostgreSQL unless an application-created ID is needed to complete an atomic graph. Timestamps are UTC `timestamptz`.

### `Contact` → `contacts`

| Field                           | Shape                            | Rule                                                      |
| ------------------------------- | -------------------------------- | --------------------------------------------------------- |
| `id`                            | UUID primary key                 | Immutable                                                 |
| `workspaceId`                   | UUID                             | Required; workspace-aware parent for every child          |
| `kind`                          | `ContactKind`                    | Required and immutable                                    |
| `reference`                     | varchar(20)                      | Required; immutable; unique within workspace              |
| `status`                        | `ContactStatus`                  | Defaults to active                                        |
| `title`                         | varchar(40), nullable            | Person only                                               |
| `firstName`                     | varchar(100), nullable           | Required for person                                       |
| `middleNames`                   | varchar(200), nullable           | Person only                                               |
| `lastName`                      | varchar(100), nullable           | Required for person                                       |
| `preferredName`                 | varchar(100), nullable           | Person only                                               |
| `organisationType`              | `OrganisationType`, nullable     | Required for organisation                                 |
| `legalName`                     | varchar(200), nullable           | Required for organisation                                 |
| `tradingName`                   | varchar(200), nullable           | Organisation only                                         |
| `registrationNumber`            | varchar(64), nullable            | Organisation only; normalized companion used for matching |
| `vatNumber`                     | varchar(32), nullable            | Organisation only; normalized companion used for matching |
| `preferredCommunicationChannel` | `CommunicationChannel`, nullable | Must not identify a restricted channel                    |
| `doNotEmail`                    | boolean                          | Defaults false                                            |
| `doNotTelephone`                | boolean                          | Defaults false                                            |
| `doNotSms`                      | boolean                          | Defaults false                                            |
| `doNotWhatsApp`                 | boolean                          | Defaults false                                            |
| `doNotPost`                     | boolean                          | Defaults false                                            |
| `mergedIntoContactId`           | UUID, nullable                   | Same-workspace contact; required only for merged status   |
| `archivedAt`                    | timestamp, nullable              | Required for archived/merged status                       |
| `createdByMembershipId`         | UUID                             | Same-workspace active actor at creation                   |
| `createdAt`, `updatedAt`        | timestamps                       | Required                                                  |

Database constraints:

- Unique `(workspaceId, id)` and `(workspaceId, reference)`.
- A person requires trimmed non-empty first and last names and cannot carry organisation-only fields.
- An organisation requires a type and trimmed non-empty legal name and cannot carry person-only fields.
- A merged contact points to another contact in the same workspace, never itself. Other statuses have no merge target.
- Archived or merged records have `archivedAt`; active records do not.
- A preferred communication channel cannot also be marked do-not-use.
- Normalized registration and VAT values are derived and maintained consistently; they are indexed for matching but not globally unique because legitimate exceptions and legacy duplicates must remain reviewable.
- No runtime hard-delete policy.

Readable references use kind-specific random identifiers such as `PER-7K4M9Q2D` and `ORG-P8T3WX6R`. They are generated server-side using an unambiguous alphabet, retried on the workspace unique constraint, and do not expose workspace volume through a sequence.

### `ContactPoint` → `contact_points`

| Field                            | Shape                 | Rule                                          |
| -------------------------------- | --------------------- | --------------------------------------------- |
| `id`, `workspaceId`, `contactId` | UUIDs                 | Composite same-workspace foreign key          |
| `kind`                           | email or telephone    | Required                                      |
| `label`                          | varchar(40), nullable | Examples: personal, work, mobile, office      |
| `value`                          | varchar(254)          | User-facing value                             |
| `normalizedValue`                | varchar(254)          | Server-normalized duplicate/search value      |
| `isPreferred`                    | boolean               | Defaults false                                |
| `archivedAt`                     | timestamp, nullable   | Historical removal instead of silent deletion |
| `createdAt`, `updatedAt`         | timestamps            | Required                                      |

Rules:

- At most one active preferred email and one active preferred telephone per contact, enforced by partial unique indexes.
- Exact normalized values are indexed within the workspace, but not unique.
- Email normalization is trim plus case normalization. Telephone normalization uses a reviewed UK-aware parser when possible; an unparseable value fails validation rather than being guessed.
- Archiving a preferred point requires choosing another active preferred point of that kind or accepting that none remains.
- A completed individual needs an active email or telephone. A completed organisation needs its own active point or a linked active primary person with one. This is an application/domain rule tested at the appraisal boundary, not a reason to weaken canonical contact validation.

### `ContactAddress` → `contact_addresses`

| Field                            | Shape                  | Rule                                      |
| -------------------------------- | ---------------------- | ----------------------------------------- |
| `id`, `workspaceId`, `contactId` | UUIDs                  | Composite same-workspace foreign key      |
| `kind`                           | address kind           | Individual, registered, or correspondence |
| `addressLine1`                   | varchar(160)           | Required                                  |
| `addressLine2`                   | varchar(160), nullable | Optional                                  |
| `locality`                       | varchar(100), nullable | Optional                                  |
| `townCity`                       | varchar(100)           | Required                                  |
| `county`                         | varchar(100), nullable | Optional                                  |
| `postcode`                       | varchar(16)            | Required and normalized for matching      |
| `countryCode`                    | char(2)                | Defaults to `GB`                          |
| `archivedAt`                     | timestamp, nullable    | Preserves replaced address history        |
| `createdAt`, `updatedAt`         | timestamps             | Required                                  |

Rules:

- A person may have one active `INDIVIDUAL` address and no organisation address kinds.
- An organisation may have one active `REGISTERED` and one active `CORRESPONDENCE` address and no individual address kind.
- If correspondence equals registered, only the registered address is stored and the UI presents it as the correspondence default.
- Partial unique indexes enforce one active address per contact and kind. A small database trigger validates that address kind matches contact kind because a cross-table check constraint cannot do so.
- Previous addresses are archived rather than overwritten, although only the current address appears by default.

### `OrganisationPersonLink` → `organisation_person_links`

| Field                    | Shape                  | Rule                                                     |
| ------------------------ | ---------------------- | -------------------------------------------------------- |
| `id`, `workspaceId`      | UUIDs                  | Workspace-owned                                          |
| `organisationContactId`  | UUID                   | Must reference an organisation contact in same workspace |
| `personContactId`        | UUID                   | Must reference a person contact in same workspace        |
| `relationshipLabel`      | varchar(100), nullable | Examples: director, employee, property contact           |
| `isPrimary`              | boolean                | Defaults false                                           |
| `startedAt`, `endedAt`   | timestamps             | Effective relationship history                           |
| `createdAt`, `updatedAt` | timestamps             | Required                                                 |

Rules:

- Composite foreign keys prevent cross-workspace links.
- A trigger verifies the two referenced contact kinds.
- Only one active primary person per organisation, enforced by a partial unique index.
- Ending a relationship preserves it. Rows are not normally deleted.
- Linking does not silently broaden branch visibility. The application must explicitly add the appropriate branch link to both contacts in the same transaction.

### `ContactBranchLink` → `contact_branch_links`

| Field                                        | Shape      | Rule                                  |
| -------------------------------------------- | ---------- | ------------------------------------- |
| `id`, `workspaceId`, `contactId`, `branchId` | UUIDs      | Same-workspace foreign keys           |
| `isPrimary`                                  | boolean    | One active primary branch per contact |
| `startedAt`, `endedAt`                       | timestamps | Preserves branch relationship history |
| `createdByMembershipId`                      | UUID       | Auditable same-workspace actor        |
| `createdAt`, `updatedAt`                     | timestamps | Required                              |

Rules:

- A contact is created with an active primary branch link in one transaction.
- Only one active link for a contact/branch pair and one active primary branch per contact.
- Branch-scoped users can create or manage links only for branches in their verified scope. Workspace-scoped authorised users can manage any branch in that workspace.
- Ending a link does not erase it. A contact with no active branch link is invalid outside a controlled merge/archive operation.
- Later property, opportunity, and instruction services add or retain branch links explicitly; an organisation-person link alone does not grant access.

## Search and duplicate candidates

Start with PostgreSQL and indexed canonical values; do not introduce a separate search service.

- Exact strong signals: normalized email, normalized telephone, normalized organisation registration number.
- Strong property-address matching belongs to Chunk 4 because no property exists in this slice.
- Weaker signals: normalized person name plus postcode, or organisation legal/trading name plus postcode.
- Searchable values: reference, person names, organisation legal/trading name, email, telephone, registration number, and postcode.
- Search defaults to active records. Include archived and Include merged are explicit filters.
- Candidate results explain which fields matched. They never merge automatically or reveal inaccessible branch records.
- For the small initial volume, normalized B-tree indexes and prefix search are sufficient. Consider `pg_trgm` only if representative-volume evidence shows a real need for fuzzy/contains search.

## Application and module boundary

Use `core/contacts/` with the existing modular-monolith layers:

```text
core/contacts/
  domain/       # validation, normalization, lifecycle and duplicate strength
  application/  # authorised use cases and transaction boundaries
  data/         # Prisma repository queries; always workspace and branch scoped
```

Server operations obtain the verified workspace membership, set transaction-local workspace and branch context, check the named permission, validate the resource/field action, perform all dependent writes in one transaction, and append a safe audit event.

Do not expose Prisma records directly to client components. Return narrow view models without normalized matching fields, audit-only metadata, or inaccessible branch relationships.

## Permissions proposal

Add these named permissions rather than checking role strings in contact code:

```text
contact.read
contact.create
contact.update
contact.archive
contact.sensitive.manage
contact.merge        # reserved for Chunk 3; grants nothing until implemented
```

Recommended bundles:

| Role                          | Permissions in this slice                              |
| ----------------------------- | ------------------------------------------------------ |
| Account Owner / Agency Admin  | All contact permissions within workspace scope         |
| Branch Manager                | All except permanent erasure, within branch scope      |
| Negotiator / Property Manager | Read, create, and routine update within branch scope   |
| Accounts                      | Read and routine update within branch scope (approved) |
| Read only                     | Read within branch scope                               |

`contact.sensitive.manage` covers kind correction through the future merge/replacement path, legal/registration identity, organisation type, branch links, archive/reactivate, and later ownership relationships. It does not grant permanent deletion. Routine update covers names, ordinary contact points, preferences, and current addresses under audit.

The owner has approved unioning permissions for multiple roles; `read_only` remains exclusive.

## Database isolation proposal

Extend the verified transaction context with server-derived values:

```text
app.membership_id
app.membership_scope_mode       # workspace or named_branches
app.allowed_branch_ids          # PostgreSQL uuid[] text representation
```

Only server code that has verified the active identity, membership, workspace, membership state, and branch rows sets these transaction-local values. Client input never supplies them.

RLS behaviour:

- Every contact table first requires `workspace_id = app.workspace_id`.
- Workspace-scoped membership can access all permitted contact rows in that workspace.
- Named-branch membership can access a contact only when an active `contact_branch_links` row intersects `app.allowed_branch_ids`.
- Child rows are accessible only when their parent contact is accessible. Organisation-person links require access to both contacts.
- New contact creation is permitted only through the application transaction that creates its authorised primary branch link. A narrowly scoped creator fallback permits the insert/returning step before that link exists; it applies only to the current verified membership and only while the contact has no active branch link.
- Platform Owner status does not grant CRM data access.
- Runtime receives no DELETE policy for these tables.
- Application filters repeat workspace and branch conditions; RLS is defence in depth, not the permission system.

The migration grants `zayto_app` only the required table/sequence operations and keeps ownership/migration authority with `zayto_migrator`. No browser Data API access is introduced.

## Audit actions

Record successful, denied, and failed sensitive operations using the existing shared audit facility:

```text
contact.create
contact.update
contact.archive
contact.reactivate
contact.point.add
contact.point.update
contact.point.archive
contact.address.add
contact.address.replace
contact.organisation_person.link
contact.organisation_person.end
contact.branch.link
contact.branch.end
contact.duplicate.review
```

Metadata contains target IDs, changed field names, branch IDs, outcome/reason codes, and request ID—not names, addresses, telephone numbers, emails, or other personal content.
